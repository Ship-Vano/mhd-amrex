# T09 — инструментирование и основа для замеров

Дата: 2026-09-03. Гейт G5, требование PERF-001.

## 1. Границы утверждений

Все числа ниже получены на **одной рабочей станции** (Apple Silicon, macOS),
без пиннинга и без эксклюзивного доступа. Это **диагностические** замеры: они
годятся для сравнения вариантов между собой на одной машине и **не являются**
результатами масштабирования. Каждая запись содержит это ограничение в поле
`caveat`. Кластерная кампания (T13) заблокирована отсутствием доступа (D-005).

## 2. Что записывается

`scripts/benchmark.py` формирует запись со схемой `schema_version: 1`:

- машина, компилятор, тип сборки, git-commit и признак «дерево грязное»;
- **≥ 1 отбрасываемый прогрев** и **≥ 5 зачётных повторов** (меньше пяти
  скрипт отказывается принимать: по ним нельзя оценить разброс);
- **медиана и MAD**, а также min/max и относительный разброс — не среднее,
  чтобы один вытесненный планировщиком прогон не смещал число;
- `compute_only` против `end_to_end` (различаются `output.write_plotfiles`),
  потому что запись plotfile'ов не относится к стоимости схемы;
- конфигурация задачи и число шагов, чтобы стоимость на ячейко-шаг
  пересчитывалась.

Нормировка `us_per_base_cell_step` считается по **базовой** сетке. Для AMR это
не work-normalized величина (мелкие уровни добавляют ячейки), и запись явно
это оговаривает — сравнивать её между разными `max_level` нельзя.

## 3. Измеренные точки (compute-only, 5 повторов + прогрев)

| случай | медиана, с | MAD, с | разброс | шагов | мкс/ячейко-шаг (база) |
|---|---:|---:|---:|---:|---:|
| Орзага–Танг $128^2$, однородная | 0.9910 | 0.0012 | 2.7 % | 323 | 0.187 |
| МГД-взрыв $128^2$, однородная | 2.1517 | 0.0634 | 19.4 % | 241 | 0.545 |
| ОТ $64^2$ + 1 уровень AMR, статическая | 0.3407 | 0.0012 | 1.1 % | 37 | 2.248 |
| ОТ $64^2$ + 1 уровень AMR, regrid каждые 4 | 0.8021 | 0.0335 | 15.0 % | 37 | 5.293 |

Разброс в 15–19 % на коротких прогонах — ровно причина, по которой отчитывается
медиана с MAD, а не одно измерение.

## 4. Профиль горячего пути

Сборка `cmake --preset profile` (`AMReX_TINY_PROFILE=ON`), случай
`inputs/amr_conservation.json` (ОТ $64^2$ + 1 уровень AMR). Inclusive-доли:

| регион | вызовов | доля |
|---|---:|---:|
| `MhdAmr::EulerStage` | 74 | 89.6 % |
| `MhdAmr::FillPatchFaces` | 148 | **29.7 %** |
| `MhdAmr::ComputeFluxesAndEmf` | 148 | 16.2 % |
| `MhdAmr::FillPatchCells` | 150 | 12.3 % |
| `MhdAmr::AverageDownAll` | 75 | 8.5 % |
| `MhdAmr::RefluxAll` | 74 | 6.6 % |
| `MhdAmr::ApplyUpdates` | 148 | 3.0 % |

Главное наблюдение: на небольшой AMR-задаче **заполнение фантомов граневого
поля дороже самой физики** — `FillPatchFaces` почти вдвое превосходит
`ComputeFluxesAndEmf`. Это указывает, куда имеет смысл оптимизировать в первую
очередь (T10), и одновременно объясняет, почему нормировка на базовые ячейки у
AMR-случаев выглядит «дорого»: постоянные накладные расходы на стык уровней при
малом числе ячеек не амортизируются.

Согласование потоков на стыке уровней (`RefluxAll` + `AccumulateFluxRegisters`)
стоит около 7 % — недорого за восстановленную консервативность (§ гейт T07).

## 5. Воспроизведение

```
cmake --preset profile && cmake --build build/profile -j 8
python3 scripts/benchmark.py --executable ./build/release/mhd2d \
    --config inputs/orszag_tang_uniform.json \
    --label "OT 128^2 uniform, compute-only" --repeats 5 --warmup 1 \
    --output benchmarks/summary/timing_ot128_uniform.json
./build/profile/mhd2d inputs/amr_conservation.json     # печатает TinyProfiler
```
